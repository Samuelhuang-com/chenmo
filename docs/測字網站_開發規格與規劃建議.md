## 二、產品概念與角色

```
┌────────────┐   問題描述 + 手寫筆畫(即時)  ┌──────────────┐
│ 問事者 User │ ─────────────────────────▶ │ 解題老師 Master │
│  (手機)     │ ◀───────────────────────── │  (電腦/平板)    │
└────────────┘      解字結果 / 解讀回覆      └──────────────┘
                         ▲
                         │ 字典資料 + AI 草稿（五行、古字、字義）
                    ┌────┴─────┐
                    │ 字庫/AI 服務 │
                    └──────────┘
```

| 角色 | 主要動作 |
|---|---|
| **問事者（User）** | 輸入 100 字內問題 → 在手寫板寫一個字 → 送出 → 等待/查看老師解讀 |
| **解題老師（Master）** | 案件列表 → 即時看筆畫順序重播 → 查看系統帶出的字資料 → 編修並回覆 |
| **管理者（Admin，後期）** | 老師帳號、字庫維護、案件稽核 |

## 三、功能規格

### 3.1 問事者端（手機優先）

**F-U1 問題描述**
- `textarea`，即時字數計數「36 / 100」，到 100 字後不能再輸入
- 字數用 `[...text].length` 算（Unicode code point），避免罕用字、Emoji 被算成 2 字
- 後端用 Pydantic 再檢查一次：`constr(max_length=100)` 搭配自訂 validator 按 code point 計數
- 文字內容由使用者用自己手機的輸入法輸入（不必另做）

**F-U2 手寫板（核心）**
- 位置：問題描述正下方，正方形宣紙底，畫「米字格」或「九宮格」淡紅輔助線
- 用 HTML5 `<canvas>` 加 Pointer Events（`pointerdown/move/up`），同時支援手指與觸控筆
- CSS 設 `touch-action: none`，避免寫字時頁面跟著捲動或縮放
- **每一筆**記錄點座標與時間戳，這是測字的關鍵資料（筆順、筆速、停頓）：
  ```json
  {
    "canvas": {"w": 300, "h": 300},
    "strokes": [
      {"seq": 1, "t0": 1728350000123,
       "points": [[0.21, 0.30, 0], [0.25, 0.31, 16], [0.40, 0.33, 48]],
       "pressure": [0.5, 0.6, 0.55]}
    ]
  }
  ```
  - 座標正規化成 0–1，不同螢幕尺寸都能還原
  - 第三個值是相對 t0 的毫秒數，重播時可以還原真實書寫速度
- 按鈕：`復原上一筆`、`清除重寫`、`送出`
- 毛筆質感：依筆速調整線寬（寫快變細、寫慢變粗），可用開源的 `perfect-freehand`

**F-U3 預測字（手寫辨識候選）**
- 手寫板下方顯示 5–8 個候選字，使用者點選來「確認自己寫的是哪個字」
- 為什麼需要：老師端才能自動帶出字資料；而且使用者寫的形狀本身（含寫歪、寫錯）也要原樣保留，因為那正是測字要看的
- 辨識方案比較：

| 方案 | 優點 | 缺點 | 建議 |
|---|---|---|---|
| **HanziLookupJS**（開源，在瀏覽器端跑） | 免費、離線、不必呼叫 API、反應快 | 草寫辨識普通；繁體要確認資料涵蓋 | ✅ MVP 首選 |
| **Zinnia + 中文模型**（Python 後端） | 可控、能放在自己的 Cloud Run 上 | 要自己部署，模型較舊 | 備案 |
| Google Input Tools 手寫端點 | 辨識率高 | 非官方公開 API，隨時可能失效，有條款風險 | ❌ 不建議正式使用 |
| 多模態 AI（把字的圖片送給模型） | 草字、潦草字也認得 | 有成本與延遲 | 後期當「進階辨識」 |

- 若候選字都不對，提供「都不是，請老師判讀」選項，字身直接交給老師

**F-U4 送出與等待**
- 送出後顯示「已呈老師」狀態頁（香爐或墨點暈開的動畫）
- 老師回覆後即時推播到頁面；可另外寄 Email 或用 LINE Notify 替代方案（LINE Notify 已停止服務，請改用 LINE Messaging API）
- 每個案件有一組不易猜的網址，例如 `/c/{case_token}`，使用者可以收藏後回來看

### 3.2 解題老師端

**F-M1 案件看板**
- 分欄：`書寫中`（即時）／`待解`／`已解`
- 顯示：問題摘要、送出時間、使用者確認的字

**F-M2 即時筆畫觀看（核心）**
- 使用者每寫完一筆（`pointerup`）就透過 WebSocket 傳給老師端，老師能「看著對方寫」
- 進階：寫的過程中每 50ms 送一批點座標，達到真正的同步書寫
- 已完成的字可以重播：
  - 播放／暫停／0.5×、1×、2× 速度
  - 每一筆用編號和不同深淺標示筆順
  - 逐筆模式：按「下一筆」一筆一筆看
- 並排顯示：使用者原跡 ↔ 標準楷書字形（看哪裡寫得不同、多一筆或少一筆）

**F-M3 字資料面板（系統自動帶出，老師編修）**

| 欄位 | 內容 | 資料來源建議 |
|---|---|---|
| 基本 | 部首、總筆畫、康熙筆畫、注音、異體字 | Unihan（`kRSKangXi`、`kTotalStrokes`）、教育部異體字字典 |
| **五行** | 字的五行屬性 + 判定依據 | 見下方說明 |
| **古字說法** | 《說文解字》原文、六書分類、甲骨／金文／小篆字形 | 說文解字（公版）、字形演變參考 |
| **字義** | 本義、引申義、常用詞 | 教育部《重編國語辭典修訂本》、《康熙字典》（公版） |
| 拆字提示 | 可拆成哪些部件、可增減筆畫變成哪些字 | 部件資料（如 CHISE IDS）＋ AI 輔助 |

**五行判定要注意：** 各家判法不同，系統要能**同時列出多種依據**，最後由老師定奪：
1. 依部首或字義（如「氵」屬水、「木」旁屬木）
2. 依康熙筆畫數的尾數（姓名學常用：1、2 木；3、4 火；5、6 土；7、8 金；9、0 水）
3. 依字音（喉、舌、齒、牙、唇音對應五行）
4. 老師自訂（覆寫）

建議做一張「五行對照表」由老師自己維護。這是老師的專業 know-how，也是網站的核心資產。

**F-M4 AI 解字草稿（建議功能）**
- 老師按「產生草稿」→ 後端把「字資料＋使用者問題＋筆畫特徵（筆數、異常筆順、停頓位置）」送給大型語言模型 → 產出一份解字草稿
- 用 **RAG 方式**：模型只能根據查到的字典原文來寫，並標註出處，避免捏造古字典故
- **AI 只出草稿，一定經過老師審閱才送出**，畫面上要明確標示「AI 草稿」

**F-M5 回覆**
- 富文本編輯（簡單版：粗體、段落）＋可插入圖片（例如老師手寫批註）
- 範本：常用開頭／結語
- 送出後即時推送到使用者頁面

### 3.3 筆畫特徵自動分析（加值功能，Phase 2）
系統可以自動算出，讓老師參考：
- 總筆數 vs 標準筆數（多寫、少寫）
- 筆順與標準筆順的差異（標準筆順資料：教育部《常用國字標準字體筆順學習網》、Make Me a Hanzi）
- 每筆耗時、筆與筆之間的停頓（猶豫點）
- 字在格子裡的位置與大小（偏上、偏左、寫得很小）

## 四、系統架構

### 4.1 技術選型

| 層 | 選擇 | 說明 |
|---|---|---|
| 後端 | **FastAPI**（Python 3.12） | REST + WebSocket 都用同一套 |
| 模板 | **Jinja2** | 伺服器端渲染，SEO 好、手機載入快 |
| 前端互動 | 原生 JS + **htmx**（選用）+ **Alpine.js**（選用） | 不必上 React；手寫板用純 JS 模組 |
| 即時通訊 | FastAPI WebSocket | 筆畫串流、老師回覆推送 |
| 跨實例廣播 | **Redis Pub/Sub**（Memorystore）或 Firestore 即時監聽 | Cloud Run 多台時才需要 |
| 資料庫 | **Firestore**（推薦起步）或 Cloud SQL（PostgreSQL） | 見 4.3 |
| 檔案 | **Cloud Storage** | 字跡 PNG 快照、老師圖片 |
| 部署 | **Cloud Run** | 你已經架過，延續即可；支援 WebSocket |
| 身分驗證 | Firebase Authentication（Google／LINE 登入）或簡易 Magic Link | 老師端一定要登入 |
| 機密 | Secret Manager | API Key、DB 密碼 |
| CI/CD | GitHub Actions → Artifact Registry → Cloud Run | 延續你熟悉的流程 |

### 4.2 Google Cloud 部署架構

```
        手機瀏覽器 / 老師瀏覽器
                │ HTTPS / WSS
        ┌───────▼────────┐
        │  Cloud Run      │  FastAPI + Jinja2
        │  (session       │  - min-instances=1（避免冷啟動斷線）
        │   affinity 開)  │  - timeout=3600s（WebSocket 上限）
        └──┬─────┬────┬──┘
           │     │    │
   Firestore  Cloud   Redis(Memorystore)  ← 多實例時才加
   (案件/筆畫) Storage  (pub/sub)
           │
     Secret Manager / AI API / 字庫資料
```

**Cloud Run + WebSocket 注意事項：**
- 單一請求最長 60 分鐘，前端要寫**自動重連**（指數退避），重連後補抓遺漏的筆畫
- 初期設 `max-instances=1` 就不需要 Redis，架構最簡單；流量變大再加 Redis Pub/Sub
- 開啟 session affinity
- 筆畫一定**同時寫入資料庫**，WebSocket 只負責「即時」，資料完整性靠 DB

### 4.3 資料模型（Firestore 版）

```
cases/{case_id}
  token: str            # 公開網址用，隨機 22 字元
  question: str         # ≤100 字
  status: drafting | submitted | answering | answered
  confirmed_char: str?  # 使用者點選的預測字
  candidates: [str]     # 辨識候選
  created_at, submitted_at, answered_at
  master_id: str?
  user_contact: {email?}  # 選填

cases/{case_id}/strokes/{seq}
  seq: int
  t0: int
  points: [[x, y, dt], ...]
  pressure: [float]?

cases/{case_id}/answer
  char_info: {wuxing: {...}, ancient: {...}, meaning: {...}}
  ai_draft: str?
  body: str             # 老師最終回覆
  sent_at

chars/{char}            # 字庫快取
  radical, strokes, kangxi_strokes, bopomofo,
  shuowen: str, liushu: str, meanings: [str],
  wuxing_by_radical, wuxing_by_strokes, wuxing_override,
  sources: [{name, url}]

masters/{uid}
  name, role, active
```

用 Cloud SQL 的話，`strokes` 可存成一個 JSONB 欄位，查詢會更方便。

### 4.4 路由規劃

**頁面（Jinja2）**
| 路徑 | 說明 |
|---|---|
| `GET /` | 首頁（品牌、怎麼用、免責聲明） |
| `GET /ask` | 問事頁：問題描述＋手寫板 |
| `GET /c/{token}` | 案件狀態／解讀結果頁 |
| `GET /master` | 老師看板（需登入） |
| `GET /master/case/{id}` | 老師解字工作台 |

**API**
| 方法 | 路徑 | 說明 |
|---|---|---|
| `POST` | `/api/cases` | 建立案件（回傳 token） |
| `POST` | `/api/cases/{token}/strokes` | 補傳筆畫（WebSocket 斷線時的備援） |
| `POST` | `/api/cases/{token}/submit` | 送出（問題＋確認字） |
| `GET` | `/api/chars/{char}` | 查字資料 |
| `POST` | `/api/master/cases/{id}/draft` | 產生 AI 草稿 |
| `POST` | `/api/master/cases/{id}/answer` | 老師送出回覆 |
| `WS` | `/ws/user/{token}` | 使用者端：上傳筆畫、接收回覆 |
| `WS` | `/ws/master` | 老師端：接收即時筆畫與新案件 |

**WebSocket 訊息格式**
```json
// User → Server
{"type": "stroke_start", "seq": 3, "t0": 1728350001000}
{"type": "stroke_points", "seq": 3, "points": [[0.4,0.5,16],[0.42,0.52,32]]}
{"type": "stroke_end", "seq": 3}
{"type": "undo", "seq": 3}
{"type": "clear"}

// Server → Master
{"type": "case_new", "case_id": "...", "question": "..."}
{"type": "stroke_points", "case_id": "...", "seq": 3, "points": [...]}

// Server → User
{"type": "answer_ready", "url": "/c/xxxx"}
```
> 注意：「復原」和「清除」也要記錄，不要直接刪資料。對測字來說，使用者「寫了又擦掉」本身就是一種訊息，老師端可以選擇要不要顯示。

## 五、視覺設計：古典沉穩

### 5.1 色彩
| 用途 | 名稱 | 色碼 |
|---|---|---|
| 背景 | 宣紙 | `#F3ECDD` |
| 主文字 | 松煙墨 | `#2B2622` |
| 次文字 | 淡墨 | `#6B625A` |
| 強調／印章 | 朱砂 | `#A8322D` |
| 輔助線 | 赭石淡紅 | `#D9A79A`（30% 透明） |
| 點綴 | 古銅金 | `#9C7C3C` |
| 深色模式背景 | 玄 | `#1C1A18` |

五行的顏色可以順勢用在標籤上：木 青 `#4A6B53`、火 赤 `#A8322D`、土 黃 `#B08A3E`、金 白 `#E8E2D4`（深底）、水 黑 `#2B2622`。

### 5.2 字型
- 標題：**思源宋體 Noto Serif TC**（Google Fonts，免費可商用）
- 內文：Noto Serif TC，字重 400
- 重點字（使用者寫的那個字、標準字形）：楷體。可用教育部標準楷書（授權方式為 CC BY-ND，請確認使用條款）或霞鶩文楷（開源，SIL OFL）
- 手機上中文 Web Font 很大，記得用 Google Fonts 的分割載入，或用 subset 子集化

### 5.3 版面元素
- 宣紙紋理背景（用一張很淡的紙紋 PNG，或 CSS noise）
- 章節標題可以用直排（`writing-mode: vertical-rl`），只放在桌機版的側邊做裝飾，手機版保持橫排易讀
- 朱砂方印當 Logo 與「送出」按鈕的視覺
- 動態一律放慢：淡入 400–600ms，墨暈擴散效果，不要彈跳動畫
- 留白多、裝飾少：古典靠留白和字型，不靠花紋堆疊

### 5.4 手機手寫板 UX 重點
- 手寫板寬度 = 螢幕寬 − 32px，正方形
- 開始寫字時自動收起鍵盤（`textarea.blur()`）
- 按鈕至少 44×44px，放在手寫板下方，拇指好按
- iOS Safari 要防止長按跳出放大鏡、選字：`-webkit-user-select: none; -webkit-touch-callout: none;`

## 九、我的規劃建議

1. **筆畫資料是核心資產，從第一天就存完整。** 座標、時間、復原紀錄都要存。之後要做分析或 AI，資料都已經在了；反過來，一開始沒存的就永遠補不回來。
2. **先做 Phase 1 的「即時觀看」再做其他。** 這是這個網站和一般「輸入一個字、自動跑出解釋」的測字網站最大的差別，也是技術風險最高的部分（手機觸控、WebSocket 斷線）。先驗證它。
3. **五行和解讀，AI 只當助理。** 測字的價值在老師的判讀。系統負責把資料備齊，判斷交給你。這樣也能避開 AI 捏造典故的風險。
4. **不用急著上前端框架。** Jinja2 + 一個寫得好的 `brush-pad.js` 模組就足夠，維護成本最低，也符合你現有的技術。
5. **WebSocket 寫一個抽象層**（`services/realtime.py`），初期用記憶體實作，之後換成 Redis 時不用改業務程式碼。
6. **先用你自己當第一位老師、親友當第一批問事者**，收集 30–50 個真實案件，再決定 Phase 3 的筆畫分析要看哪些指標。

## 附錄 A：手寫板核心程式骨架（brush-pad.js）

```javascript
export class BrushPad {
  constructor(canvas, { onStrokeStart, onPoints, onStrokeEnd }) {
    this.c = canvas;
    this.ctx = canvas.getContext('2d');
    this.strokes = [];
    this.cur = null;
    this.cb = { onStrokeStart, onPoints, onStrokeEnd };
    this.buffer = [];
    this._resize();
    canvas.style.touchAction = 'none';
    canvas.addEventListener('pointerdown', e => this._down(e));
    canvas.addEventListener('pointermove', e => this._move(e));
    canvas.addEventListener('pointerup',   e => this._up(e));
    canvas.addEventListener('pointercancel', e => this._up(e));
    setInterval(() => this._flush(), 50);   // 每 50ms 批次送出
  }
  _resize() {
    const dpr = window.devicePixelRatio || 1;
    const r = this.c.getBoundingClientRect();
    this.c.width = r.width * dpr; this.c.height = r.height * dpr;
    this.ctx.scale(dpr, dpr);
    this.w = r.width; this.h = r.height;
  }
  _pt(e) {
    const r = this.c.getBoundingClientRect();
    return [ (e.clientX - r.left) / this.w,
             (e.clientY - r.top)  / this.h,
             Math.round(performance.now() - this.cur.tStart) ];
  }
  _down(e) {
    this.c.setPointerCapture(e.pointerId);
    this.cur = { seq: this.strokes.length + 1, t0: Date.now(),
                 tStart: performance.now(), points: [], pressure: [] };
    this.cb.onStrokeStart?.(this.cur.seq, this.cur.t0);
    this._add(e);
  }
  _move(e) { if (this.cur) this._add(e); }
  _add(e) {
    const p = this._pt(e);
    this.cur.points.push(p);
    this.cur.pressure.push(e.pressure || 0.5);
    this.buffer.push(p);
    this._draw();
  }
  _up() {
    if (!this.cur) return;
    this._flush();
    this.strokes.push(this.cur);
    this.cb.onStrokeEnd?.(this.cur.seq);
    this.cur = null;
  }
  _flush() {
    if (this.cur && this.buffer.length) {
      this.cb.onPoints?.(this.cur.seq, this.buffer.splice(0));
    }
  }
  _draw() { /* 用 perfect-freehand 依速度繪製毛筆筆觸 */ }
  undo()  { /* 記錄 undo 事件，重繪 */ }
  clear() { /* 記錄 clear 事件，重繪 */ }
}
```

## 附錄 B：FastAPI WebSocket 骨架

```python
# app/services/realtime.py
from collections import defaultdict
from fastapi import WebSocket

class Hub:
    """初期記憶體版；之後可換 RedisHub，介面不變"""
    def __init__(self):
        self.masters: set[WebSocket] = set()
        self.users: dict[str, WebSocket] = {}

    async def to_masters(self, msg: dict):
        for ws in list(self.masters):
            try:
                await ws.send_json(msg)
            except Exception:
                self.masters.discard(ws)

    async def to_user(self, token: str, msg: dict):
        if ws := self.users.get(token):
            await ws.send_json(msg)

hub = Hub()

# app/routers/ws.py
from fastapi import APIRouter, WebSocket, WebSocketDisconnect
from app.services.realtime import hub
from app.repositories import cases_repo

router = APIRouter()

@router.websocket("/ws/user/{token}")
async def user_ws(ws: WebSocket, token: str):
    case = await cases_repo.get_by_token(token)
    if not case:
        await ws.close(code=4404); return
    await ws.accept()
    hub.users[token] = ws
    try:
        while True:
            msg = await ws.receive_json()
            await cases_repo.append_event(case.id, msg)   # 先落地
            await hub.to_masters({**msg, "case_id": case.id})  # 再廣播
    except WebSocketDisconnect:
        hub.users.pop(token, None)
```
